# Security Scanning (Security Analysis Mode)

## Overview
Security Analysis Mode is a deliberately separate pipeline from the main analyze/AI-suggestions flow: it runs Bandit plus a custom pattern-matching rules engine against an `Analysis`'s source code, has AI enrich each finding with an explanation and remediation, aggregates everything into a scored report, and caches that report on `Analysis.security_report` — never mixed into the main `issues` field or its quality score. It exists because Bandit is an AST tool scoped to Python "dangerous call" patterns and has no notion of framework-level concerns (Django DEBUG, CSRF, auth decorators); the custom rules engine fills that gap. The same pipeline (`SecurityAnalysisService`) is also reused, with a request-wide time budget injected, by the GitHub PR review pipeline.

## Key files
- `backend/analyses/security_views.py` — `SecurityAnalysisView`: GET/POST `/api/analysis/<id>/security/`.
- `backend/analyses/services/types.py` — shared dataclasses/enums: `SecurityFinding`, `ScannerUnavailable`, `Severity`, `RiskLevel`, `VulnerabilityType`, `BaseSecurityScanner` interface.
- `backend/analyses/services/bandit_service.py` — `BanditScanner`, runs `python -m bandit -f json` on a temp file, normalizes results into `SecurityFinding`s, maps Bandit test IDs → `VulnerabilityType` and escalates a fixed set of rule IDs to `CRITICAL`.
- `backend/analyses/services/custom_rules_service.py` — `CustomRulesScanner`, line/regex-based checks (DEBUG=True, CSRF disabled, hardcoded secrets, unsafe file upload, missing auth decorator/permission_classes, lightweight path-traversal taint tracking).
- `backend/analyses/services/ai_security_service.py` — `AISecurityService`, sends already-detected findings (not raw source) to `ai/client.generate_text` in one batched call to get `explanation`/`remediation` text.
- `backend/analyses/services/report_generator.py` — `SecurityReportGenerator.build_report()`: scores findings, computes risk level, sorts/shapes the final dict.
- `backend/analyses/services/security_service.py` — `SecurityAnalysisService`, the orchestrator/only entry point views should import: runs scanners → dedupes → AI-enriches → builds report.
- `backend/analyses/models.py` — `Analysis.security_report` (`JSONField(default=dict, blank=True)`).
- `backend/analyses/serializers.py` — `SecurityReportSerializer` (+ `SecuritySummarySerializer`, `SecurityVulnerabilitySerializer`, `ScannerUnavailableSerializer`), the API response contract.
- `backend/analyses/analysis_urls.py` — registers the `security/` route.
- `backend/analyses/services/tests.py`, `backend/core/tests_execution_budget.py` — scanner/service/budget-interaction tests.
- `backend/github_integration/services/pr_analysis_service.py` — the other caller of `SecurityAnalysisService`, wired with a `RequestBudget`.

## How it works
1. **Trigger**: `POST /api/analysis/<id>/security/` (optionally `?regenerate=true`). `SecurityAnalysisView._get_owned_completed_analysis` requires the analysis be owned by `request.user` and `status == COMPLETED` before a scan can run (400 otherwise). If a cached `security_report` already exists and `regenerate` isn't set, the cached report is returned immediately with `{"cached": true}` — no re-scan. `GET` only ever returns the cache (404 if none has been run yet).
2. **Orchestration**: `SecurityAnalysisService(scanners=[BanditScanner(), CustomRulesScanner()]).analyze(source_code, language, filename)` (defaults used by the view; `pr_analysis_service` passes its own instances with a `budget`). Steps: `_run_scanners` → `_deduplicate` → `ai_service.enrich` → `report_generator.build_report`.
3. **Bandit**: only invoked when `language == 'Python'` (`_LANGUAGE_RESTRICTED_SCANNERS = {'bandit': 'Python'}` in `security_service.py`) — for any other language it's skipped silently, not reported as unavailable. Runs out-of-process via `sys.executable -m bandit -f json <tempfile>` with a 20s timeout (`BANDIT_TIMEOUT_SECONDS`); a request budget (when injected) can shrink or skip this. Findings map Bandit's `test_id`/`issue_severity` into `SecurityFinding` via `_RULE_TYPE_MAP`/`_SEVERITY_MAP`, with `_CRITICAL_RULE_IDS` (SQLi, pickle, eval, shell=True, wildcard injection) force-escalated to `CRITICAL` regardless of Bandit's own confidence.
4. **Custom rules**: `CustomRulesScanner.scan()` always runs (any language) and does three passes: `_scan_line_rules` (regex table `_LINE_RULES` for DEBUG=True, csrf_exempt/CSRF_COOKIE_SECURE=False, hardcoded SECRET_KEY/API_KEY/etc., `request.FILES`), `_scan_missing_auth` (flags `def view(request...)` functions with no `@login_required`/`@permission_classes`/`@api_view` in the 3 preceding lines, and DRF view classes with no/permissive `permission_classes` — suppressed when a passed-in `settings_source` shows a restrictive `DEFAULT_PERMISSION_CLASSES`), and `_scan_path_traversal` (tracks whether a variable passed to `open()` was recently assigned from `request.GET/POST/FILES`/`input()`/`sys.argv` and not since sanitized via `os.path.basename`/`secure_filename`). Rules are just entries in the `_LINE_RULES` list or additional `_scan_*` methods — adding one means extending that table/adding a method, not touching the pipeline.
5. **Dedup**: `SecurityAnalysisService._deduplicate` keeps only the first finding per `(vulnerability_type, line_number)` key, so two scanners flagging the same line don't double-count.
6. **AI enrichment**: `AISecurityService.enrich()` batches every finding into one `generate_text` call (system prompt in `_SYSTEM_INSTRUCTION`) asking only for `explanation`/`remediation` per finding, in order — the AI is never given raw source or asked to decide what's a vulnerability, only to describe already-found ones. Response is parsed as JSON (fenced-code-block stripped), padded/truncated to match `expected_count`. On any exception, or `BudgetExceeded` from the injected budget, `entries` becomes `[None] * len(findings)` and each finding falls back to `_fallback_explanation`/`_fallback_remediation` (built from the scanner's own `description`/`title`) — the raw findings and their severity/score are never lost, only the AI-authored prose.
7. **Report + caching**: `SecurityReportGenerator.build_report()` computes `score` (100 minus `SEVERITY_PENALTIES` per finding: critical 30/high 20/medium 10/low 5, floored at 0), `risk_level` via `_RISK_LEVEL_THRESHOLDS`, a `summary` (counts per severity + total), the sorted `vulnerabilities` list (`SecurityFinding.to_dict()`), `scan_complete` (`False` if any scanner reported `ScannerUnavailable`), and `scanners_unavailable`. The view stores this dict directly on `analysis.security_report` and saves with `update_fields=['security_report', 'updated_at']` — a full overwrite, no merge/versioning; the previous report is gone once regenerated.
8. **API surface**: both GET and POST return `SecurityReportSerializer(report).data` plus a `cached` boolean (`True` for GET/served-from-cache POST, `False` for a freshly generated POST, which also returns HTTP 201).
9. **Frontend**: as of this writing, **no frontend UI consumes this endpoint or `security_report`** — `frontend/src/lib/resources.js` has no security-scan function, and no component reads `security_report`/`vulnerabilities`/`risk_level`/`scan_complete`. What looks like "security" UI in `AnalysisTabs.jsx` and `IssueGroups.jsx` is unrelated: it groups the *main* AI-suggestions/GitHub-PR-issues list by `category === 'security'` / `source === 'security'`, which comes from the regular analyze flow and `pr_analysis_service`, not from this pipeline's `security_report`.

## Gotchas / non-obvious behavior
- `Analysis.security_report` is completely separate from `Analysis.issues` and never affects `Analysis.quality_score` — the main analyze flow and Security Analysis Mode do not interact except by both reading the same `Analysis.source_code`.
- A security scan can only be started once the parent `Analysis.status == COMPLETED`; running it against a pending/failed analysis 400s.
- Caching is a simple overwrite keyed by nothing but the `Analysis` row itself: `POST` without `?regenerate=true` short-circuits to the cached report; with it, the old report is fully replaced (no history kept, no separate cache key/versioning).
- A scanner that can't run (Bandit missing/timed out/unparsable JSON, or any scanner raising) does **not** silently produce a clean-looking report — it's recorded in `scanners_unavailable` and flips `scan_complete` to `False`, specifically so a failed scan can't be misread as "no vulnerabilities found." `ScannerUnavailable.reason` distinguishes `not_installed`, `timeout`, `unparsable_output`, `error`, and `budget_exhausted` (the budget-clamped variant used by the PR pipeline, deliberately not called `timeout` so it doesn't look like Bandit's own fault).
- Bandit only ever runs for `language == 'Python'`; for every other language only `CustomRulesScanner` runs, and Bandit's absence isn't reported as "unavailable" (it's just not applicable).
- AI-enrichment failure (exception or exceeded budget) never drops or blocks findings — it only means `explanation`/`remediation` fall back to scanner-generated text; the finding, its severity, and the overall score are computed before enrichment and are unaffected by an AI outage. Same 503-on-total-failure convention as the rest of `ai/client.py`'s call sites is *not* used here — an AI failure inside `analyze()` degrades gracefully instead of raising; only a failure in the surrounding view (e.g. from `SecurityAnalysisService().analyze(...)` itself, such as Bandit/report-generation blowing up unexpectedly) returns the 503 "Security analysis is currently unavailable."
- Score is unaffected by scanner unavailability by design (`report_generator.py` comment: "a scanner failing is not evidence of vulnerabilities").
- `BanditScanner` invokes bandit via `sys.executable -m bandit`, not a bare `bandit` on `PATH` — important if a similar subprocess integration is added elsewhere, since a venv that was never "activated" won't have the console script on `PATH`.
- The exact same `SecurityAnalysisService`/`BanditScanner`/`AISecurityService`/`CustomRulesScanner` classes back the GitHub PR review pipeline (`github_integration/services/pr_analysis_service.py`), constructed there with an injected `RequestBudget` (`core/execution_budget.py`, stages `STAGE_BANDIT`/`STAGE_AI_ENRICHMENT`) so a webhook-triggered PR review can't run indefinitely; the `Analysis`-backed view path (`security_views.py`) never passes a budget, so it keeps the older unbounded behavior (flat 20s Bandit timeout, no AI-call deadline).
- `CustomRulesScanner`'s missing-auth/authorization checks accept an optional `settings_source` (the target repo's Django settings file content) to know whether `DEFAULT_PERMISSION_CLASSES` is already restrictive; the `Analysis`-backed view path never supplies this (`settings_source=''`), so it always treats DRF classes with no explicit `permission_classes` as worth flagging — only the PR pipeline (which can fetch the repo's settings file) suppresses that noise.

## Related features
- analysis-engine (shares the `Analysis` model; main analyze flow's `issues`/`quality_score` are computed independently by `analyses/engine.py`)
- ai-chat / ai-client (`ai/client.py`'s `generate_text` is reused for remediation/explanation text, same as the floating chat and per-analysis AI suggestions)
- github-integration (`pr_analysis_service.py` reuses the identical scanner pipeline for automatic PR review, with a request-wide execution budget)
- frontend-app (no dedicated UI currently renders `security_report` — a gap, not a design choice documented anywhere in code)
