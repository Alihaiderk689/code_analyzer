# Infra & Cross-Cutting Concerns

## Overview
This covers the plumbing shared by every feature app: the single `.env`-driven settings module and its `ENVIRONMENT` flag, two unrelated rate-limiting systems (DRF throttle scopes vs. domain-specific daily quotas), a project-wide JSON exception handler, a structured logging formatter, how static/media files are served (WhiteNoise vs. nginx vs. Django's dev file server), the staff-only admin API, and the Docker Compose container topology. None of this is feature logic — it's the substrate every other app (`accounts`, `analyses`, `ai`, `chat`, `github_integration`) sits on.

## Key files
- `backend/config/settings.py` — single `.env`, `ENVIRONMENT`-driven config (DEBUG, DB, cookies, HSTS), throttle rates, cache, Celery, logging.
- `backend/core/settings_validation.py` — `validate_allowed_hosts()`, fails boot in production on `ALLOWED_HOSTS=*` or empty.
- `backend/core/throttling.py` — `ScopedIdentityRateThrottle` and all named throttle subclasses.
- `backend/chat/rate_limit.py` — daily message quota, local-midnight reset via client-reported `tz_offset_minutes`.
- `backend/core/exceptions.py` — `custom_exception_handler`, the DRF `EXCEPTION_HANDLER`.
- `backend/core/logging_formatters.py` — `StructuredFormatter`, renders `extra={...}` as trailing JSON.
- `backend/core/cache.py` — `ResilientRedisCache`, fail-open Redis wrapper backing throttle counters.
- `backend/config/urls.py` — root URLconf; media route served by Django `django.views.static.serve` in every environment (not DEBUG-gated).
- `backend/adminapi/views.py`, `urls.py`, `serializers.py` — staff-only admin endpoints (users, analyses, stats).
- `docker-compose.yml` — `db`, `redis`, `backend`, `celery_worker`, `frontend` services; no `celery_beat`.
- `backend/Dockerfile` — non-root user, gunicorn `--timeout 120`, `ENTRYPOINT ["./entrypoint.sh"]`.
- `backend/entrypoint.sh` — runs `migrate`/`collectstatic` only when the command is `gunicorn`.
- `frontend/nginx.conf` — reverse-proxies `/api/`, `/admin/`, `/static/` to `backend:8000`; serves `/media/` directly from a shared volume.

## How it works

### Settings & environment
`config/settings.py` loads exactly one `.env` file (`load_dotenv(BASE_DIR / '.env')`). `ENVIRONMENT` is read from the env, normalized (`.strip().lower()`), and validated against `{'development', 'production'}` — any other value raises `ImproperlyConfigured` at import time rather than silently defaulting. Everything downstream derives from it:
- `DEBUG = ENVIRONMENT == 'development'`.
- `ALLOWED_HOSTS` goes through `validate_allowed_hosts()` (`core/settings_validation.py`), which only enforces anything when `ENVIRONMENT == 'production'`: rejects `[]` (empty list would 400 every request under `DEBUG=False`) and rejects `'*'` (defeats Host-header validation, which password-reset link generation and other code relies on).
- Database: `ENVIRONMENT == 'production'` → `DATABASE_URL_PROD` (Supabase); otherwise `DATABASE_URL_DEV` (local Postgres). Both are required env vars (`os.environ[...]`, no default) for the selected branch. Supabase's pgbouncer transaction-mode pooler needs `DISABLE_SERVER_SIDE_CURSORS = True`, translated from a `?pgbouncer=true` query flag `dj_database_url` would otherwise leave in `OPTIONS` where psycopg2 chokes on it.
- Cookies: `AUTH_COOKIE_SECURE = ENVIRONMENT == 'production'`; `AUTH_COOKIE_SAMESITE` is `'None'` in production (requires `Secure`, supports frontend/backend on genuinely different domains) and `'Lax'` in dev (sufficient since dev frontend/backend differ only by port — same "site"). `CSRF_COOKIE_SAMESITE` mirrors it. `CSRF_COOKIE_DOMAIN` comes from `COOKIE_DOMAIN` env var (leading-dot form for "this domain and all subdomains"), unset by default (host-only cookie).
- Production-only hardening: `SECURE_SSL_REDIRECT`, `SESSION_COOKIE_SECURE`, `CSRF_COOKIE_SECURE`, and HSTS (`SECURE_HSTS_SECONDS = 31536000`, `SECURE_HSTS_INCLUDE_SUBDOMAINS = True`, deliberately **no** `SECURE_HSTS_PRELOAD` — preload submission is a one-way door, accepted as a known `manage.py check --deploy` W021 warning). HSTS is scoped to production only because `SecurityMiddleware` emits it for any request it considers secure (including a local `https://` tunnel), and the header is sticky in the browser once cached.
- `SECURE_CONTENT_TYPE_NOSNIFF`, `SECURE_REFERRER_POLICY = 'strict-origin-when-cross-origin'`, `X_FRAME_OPTIONS = 'DENY'` apply in every environment. CSP/Permissions-Policy aren't Django 4.2 settings — handled by `core/middleware.py`'s `SecurityHeadersMiddleware` instead, placed as the outermost middleware so its response phase runs last (covers even short-circuited responses like a WhiteNoise static hit or CSRF rejection).
- `_RUNNING_TESTS = 'test' in sys.argv` — a single flag used in three places: widens every throttle rate in `_THROTTLE_RATES` to `'1000000/day'`, drops root/`github_integration` logger level to `WARNING` (vs `INFO`), and disables `PWNED_PASSWORDS_ENABLED` (no live HIBP HTTPS call during tests).
- Optional-at-boot integrations (Brevo email, Groq/Gemini/OpenRouter AI keys, Google Sign-In client ID, GitHub OAuth/webhook/encryption keys) all default to `''` and fail lazily (`ImproperlyConfigured` or a clear 503) on first real use rather than blocking app startup — same pattern throughout.
- `CACHES`: `core.cache.ResilientRedisCache` pointed at `CACHE_REDIS_URL` (falls back to `CELERY_BROKER_URL`) when set and not running tests; otherwise per-process `LocMemCache`. This cache backs DRF throttle counters — previously per-worker `LocMemCache` meant the real limit was `rate × worker_count`; Redis makes it a shared counter across gunicorn workers.

### Rate limiting (two systems)
**System 1 — DRF throttle scopes** (`core/throttling.py` + `DEFAULT_THROTTLE_RATES` in settings.py). Built on `SimpleRateThrottle`, not DRF's built-in `ScopedRateThrottle`, because `ScopedRateThrottle` reads its scope from a `throttle_scope` attribute on the *view* — easy to forget, and the view then silently never throttles. Instead every scope is its own throttle *class* with `scope` set on the class itself, so forgetting to set it up is a `NameError`/import failure, not silent no-op.
- `ScopedIdentityRateThrottle` base: keys by `request.user.pk` when authenticated, else IP (`get_ident`) — one base class serves both anonymous endpoints (login, register) and authenticated ones (AI, analysis creation).
- Scopes and rates (`_THROTTLE_RATES` in settings.py): `anon` 60/min, `user` 300/min (blanket, applied to every view via `DEFAULT_THROTTLE_CLASSES`); `login` 10/min; `register` 5/hour; `password_reset` 20/hour; `otp_verify` 20/hour (IP-level backstop); `otp_verify_account` 10/hour (keyed by IP **+** SHA-256-hashed target email, via `OtpVerifyAccountRateThrottle` — hashed so Redis key space doesn't enumerate recently-attempted emails); `otp_resend` 5/hour; `ai` 30/min; `analysis_create` 30/min.
- `OtpVerifyAccountRateThrottle.get_cache_key` returns `None` (no throttling from this class) when the request body has no usable email — serializer validation catches that case, and `otp_verify` still covers it.
- All rates get replaced with `'1000000/day'` under `_RUNNING_TESTS` — see Gotchas.

**System 2 — domain-specific daily quotas**, database-derived, not cache-counter-based. Canonical example: `chat/rate_limit.py`'s `DAILY_MESSAGE_LIMIT = 3` for "Chat with Your Code" — global per user across every analysis/conversation (not per-conversation, else trivially dodged by starting a new analysis). No separate counter model: usage is `ChatMessage.objects.filter(conversation__analysis__owner=user, role=USER, created_at__gte=window_start).count()`. Resets at the **user's own local midnight**, not a rolling 24h window or server-time midnight — the client sends `tz_offset_minutes` (JS `Date.getTimezoneOffset()` convention: UTC minus local, e.g. `-300` for UTC+5) on every quota-relevant request, since the server can't otherwise know the caller's timezone. `_local_midnight_boundary()` clamps the offset to `[-14h, +12h]` (real-world UTC offset range) so a malformed/malicious value can't shift the boundary somewhere nonsensical. `get_rate_limit_status()` returns `{limit, used, remaining, reset_at}`; `reset_at` is only set once the quota is exhausted (next local midnight). The GitHub file-check quota follows the same domain-specific-quota pattern (per docstring reference), separate from this chat one.

### Error handling
`core/exceptions.py`'s `custom_exception_handler` is `REST_FRAMEWORK['EXCEPTION_HANDLER']`. Flow:
1. Delegates to DRF's own `exception_handler` first — if it returns a response (i.e. the exception is an `APIException`/`Http404`/`PermissionDenied`), that's kept, except `Throttled` gets its `detail` rewritten to a friendlier message including the wait time (`'Too many requests. Try again in {N} second(s).'` or a generic message if `wait` is `None`).
2. If DRF's handler returns `None` (anything else — bugs, DB errors, unexpected third-party exceptions), this handler catches it instead of letting it fall through to Django's HTML 500 page (useless to a JSON API's frontend, and in `DEBUG` mode a traceback-leak risk).
3. `OperationalError`/`InterfaceError` (dropped DB connection, exhausted pooler) get their own branch: logged at `error` level (not `exception` — the traceback is always the same connection-teardown stack, no diagnostic value) and returned as `503` "Service temporarily unavailable" — deliberately no automatic retry (retrying into an exhausted pooler turns a blip into an outage).
4. Everything else: `logger.exception('unhandled_exception', extra={'path', 'method'})` (full traceback, server-side only), then `500` — body includes `exception` class name and `str(exc)` only when `settings.DEBUG` is true, otherwise a generic "An unexpected error occurred" message.

### Structured logging
`core/logging_formatters.py`'s `StructuredFormatter` (registered as the `structured` formatter, used by the `console` handler in `LOGGING`) computes `_STANDARD_RECORD_KEYS` once (every attribute a vanilla `LogRecord` carries, plus `message`/`asctime`) and, on each `format()` call, diffs the record's `vars()` against that set — anything left over is what was passed via `extra={...}`. It appends that as `json.dumps(extra, default=str)` after the normal formatted line; if `extra` is empty, or the dict isn't JSON-serializable even with `default=str`, it falls back to the plain formatted line (`TypeError` caught). Without this formatter, Python's default `Formatter` silently drops everything passed via `extra` — it's stored on the record but never rendered. Heavily relied on by `github_integration` (OAuth, webhook signature checks, Celery task logs, GitHub API request/comment-posting failures) and by `core/exceptions.py`'s own `unhandled_exception`/`database_unavailable` log calls.
Log levels: root and `github_integration` loggers are `WARNING` under `_RUNNING_TESTS`, `INFO` otherwise (tests deliberately exercise failure paths like invalid signatures/exhausted retries, which would print noisily at `INFO`). `django` logger is always `WARNING`.

### Static & media files
- **Static** (`STATIC_URL = 'static/'`, `STATIC_ROOT = BASE_DIR / 'staticfiles'`): served by WhiteNoise in every environment (`whitenoise.middleware.WhiteNoiseMiddleware`, placed directly after `SecurityMiddleware` per WhiteNoise's own setup docs) — `django.contrib.staticfiles` only auto-serves under `runserver`/`DEBUG=True`, and there's no CDN/separate static server in front of gunicorn. `STATICFILES_STORAGE = 'whitenoise.storage.CompressedManifestStaticFilesStorage'` adds content hashes to filenames so a new deploy's hashed assets never collide with stale browser-cached ones.
- **Media** (`MEDIA_URL = '/media/'`, `MEDIA_ROOT = BASE_DIR / 'media'`, user avatars): `config/urls.py` registers `django.views.static.serve` directly (not via `django.conf.urls.static.static()`, which is itself a DEBUG-only no-op) for `^media/(?P<path>.*)$`, **in every environment**, not DEBUG-gated. This was previously DEBUG-gated but that broke the Render deployment (no nginx in front of gunicorn there) — avatars 404'd with `DEBUG=False` while uploads kept succeeding. `django.views.static.serve` uses `safe_join` internally so path traversal isn't a concern; it's just not a fast/cached path, judged acceptable since avatars are small, public, and infrequently fetched.
- **In Docker Compose**, nginx (`frontend/nginx.conf`) serves `/media/` directly from the `media_data` volume shared with `backend`/`celery_worker` (`location /media/ { alias /usr/share/nginx/media/; expires 7d; ... }`) and never reaches Django's `serve` view at all — it's a pure disk read. `/api/`, `/admin/`, `/static/` are reverse-proxied to `backend:8000` (`proxy_read_timeout 120s`, to cover slow AI calls/PDF report generation).

### Admin API
`backend/adminapi/` — four `APIView`s, all gated by `IsAdminUser` (DRF's built-in permission: `request.user.is_staff`, distinct from the per-user `owner=request.user` object-scoping pattern used everywhere else — admin views see *all* users' data, not just their own):
- `AdminUserListView` (`GET /api/admin/users/`) — lists users with `analyses_count` annotation and `profile.is_verified`; filters by `q` (username/email icontains) and `is_active`.
- `AdminUserDeleteView` (`DELETE /api/admin/users/<pk>/`) — hard-deletes a user; refuses (400) if `pk == request.user.id` (can't self-delete via this endpoint).
- `AdminAnalysisListView` (`GET /api/admin/analysis/`) — lists all `Analysis` rows (not owner-scoped) with owner id/username/email; filters by `status`, `language` (iexact), `owner_id`.
- `AdminStatsView` (`GET /api/admin/stats/`) — aggregate counts: users (total/active/staff/verified/joined last 7d/30d) and analyses (total + per-`Status` counts + total lines of code/issues + average quality score of `COMPLETED` analyses).
No admin-specific throttle scope — falls through to the blanket `user` (300/min) throttle like any authenticated endpoint. Serializers (`adminapi/serializers.py`): `AdminUserSerializer`, `AdminAnalysisSerializer` — flat, read-only, no write/update endpoints exist in this app at all (user deletion is the only mutation, and it's a hard delete not a PATCH).

### Container topology (Docker)
`docker-compose.yml` services: `db` (Postgres 16), `redis` (7), `backend` (gunicorn), `celery_worker`, `frontend` (nginx + built SPA). **No `celery_beat` service** — this app has no scheduled/periodic tasks, only webhook-triggered Celery jobs.
- `backend` has **no port published to the host** — commented out by default (`# ports: - "${BACKEND_PORT:-8000}:8000"`). nginx (`frontend` service, published on `${FRONTEND_PORT:-80}`) is the *only* ingress into the stack, including the GitHub OAuth callback (`GITHUB_OAUTH_REDIRECT_URI` must point through nginx's `/api/` proxy, never a direct backend port).
- `backend` and `celery_worker` both build from `./backend` (same image), `celery_worker` overriding the Dockerfile's default `CMD` with `command: celery -A config worker --loglevel=info`. `backend/entrypoint.sh` only runs `python manage.py migrate --noinput` and `collectstatic` when `"$1" = "gunicorn"` — so `celery_worker`'s command (`celery ...`) skips both. `celery_worker`'s `depends_on: backend: condition: service_healthy` means it only starts once the backend's healthcheck passes, which only passes after migrate has already run — so the schema is guaranteed current by the time Celery starts, without two containers racing to apply the same migration concurrently.
- `backend`'s healthcheck hits `http://localhost:8000/api/health/` from inside the container.
- Both `backend` and `celery_worker` mount the `media_data` volume at `/app/media`; `frontend` mounts the same volume read-only at `/usr/share/nginx/media`.
- `docker-compose.yml` overrides `ENVIRONMENT`, `DATABASE_URL_DEV` (pointed at the `db` service name, not `localhost`), `CELERY_BROKER_URL`/`CELERY_RESULT_BACKEND` (pointed at `redis` service), `ALLOWED_HOSTS`, `CORS_ALLOWED_ORIGINS`, `FRONTEND_URL` on top of whatever `.env` (loaded via `env_file: .env`) provides — because a developer's non-Docker `.env` might legitimately say `localhost` meaning something different in that context.
- `backend/Dockerfile`: runs as non-root `appuser`; default `CMD` is `gunicorn config.wsgi:application --bind 0.0.0.0:8000 --workers 3 --timeout 120` — the 120s timeout is sized to sit above the bounded worst case of the in-request AI fallback chain (3 providers × `AI_REQUEST_TIMEOUT_SECONDS`, default 30s = 90s) and the GitHub repository-context analysis budget (`GITHUB_CONTEXT_REQUEST_BUDGET_SECONDS`, default 90s) — gunicorn's own 30s default previously killed those requests mid-chain, producing a raw 502 instead of the intended clean 503.

## Gotchas / non-obvious behavior
- **`_RUNNING_TESTS` exists because Django's test client reuses one `REMOTE_ADDR` for the whole run and `LocMemCache` persists for the whole test-run process.** Without relaxing throttle rates to `1000000/day`, unrelated tests would bleed into each other's shared IP-keyed throttle counters and start failing nondeterministically depending on test order. Same flag also silences `PWNED_PASSWORDS_ENABLED` (no live HTTPS call to the HIBP API on every password-setting test) and quiets logging to `WARNING` (tests deliberately trigger failure paths that would otherwise print at `INFO`).
- **`ScopedIdentityRateThrottle` exists instead of DRF's built-in `ScopedRateThrottle`** because the built-in reads its scope from a `throttle_scope` attribute set on the *view* — trivial to forget, and the view then silently never throttles anything (no error, no warning). Making scope a class attribute on a dedicated throttle subclass per endpoint fails loudly (import/reference error) instead.
- **Media is *not* DEBUG-gated in Django, despite the `django.conf.urls.static.static()` convention suggesting it should be.** It used to be; that broke the Render deployment, which has no nginx in front of gunicorn, so `DEBUG=False` made every avatar 404 while uploads kept succeeding. In Docker Compose, nginx intercepts `/media/` before it ever reaches Django (serving straight from the shared `media_data` volume), so Django's `serve` view is dead code in that topology but load-bearing in the Render one.
- **`entrypoint.sh` only runs `migrate`/`collectstatic` when the container's command is `gunicorn`.** `celery_worker` uses the identical image but a different `command:`, so it skips both — this is what prevents two containers starting simultaneously from racing to apply the same migration. `celery_worker`'s `depends_on: backend: condition: service_healthy` closes the remaining race: it only starts after backend's healthcheck (which requires the app to be up post-migrate) passes.
- **No `celery_beat` service** — there is nothing here that runs on a schedule; every Celery task is triggered by a webhook delivery, not a cron/periodic schedule.
- **`backend` publishes no port to the host at all.** nginx is the sole ingress, including for the GitHub OAuth callback — `GITHUB_OAUTH_REDIRECT_URI` must resolve through nginx's proxy, not a direct `:8000`. Uncommenting the `ports:` block in `docker-compose.yml` for local debugging bypasses nginx (and CORS/CSRF assumptions tied to the single-origin setup) entirely.
- **`ResilientRedisCache` (`core/cache.py`) makes DRF throttles fail *open*, not closed, during a Redis outage** — a cache miss reads as "no history," so requests are allowed through rather than the whole API 500ing. This is a deliberate trade-off: throttling is a rate control, not an authorization control, and the defenses that actually stop brute force (OTP attempt lockout via `select_for_update`, chat/GitHub daily quotas) are database-backed and unaffected by Redis being down.
- **`AdminUserDeleteView` hard-deletes** (`user.delete()`, not a soft-delete/deactivate) and is the only mutation endpoint in `adminapi` — no PATCH/update endpoints exist there at all.
- Admin endpoints use `IsAdminUser` (staff flag), a different authorization model from the `owner=request.user` object-scoping pattern used by every other app's endpoints — don't apply owner-scoping conventions when touching `adminapi`, and don't apply `IsAdminUser` conventions when touching per-user endpoints.

## Related features
- `github-integration` — heaviest consumer of `StructuredFormatter` (OAuth, webhook signature verification, Celery task logs); `GITHUB_OAUTH_REDIRECT_URI`/`GITHUB_WEBHOOK_BASE_URL` routing depends on nginx being the sole ingress described here.
- `ai-chat` (`chat/rate_limit.py`) — the canonical domain-specific daily-quota implementation documented above.
- `auth-accounts` — `AUTH_COOKIE_SECURE`/`AUTH_COOKIE_SAMESITE`/`CSRF_COOKIE_DOMAIN` cookie flags and the `login`/`register`/`password_reset`/`otp_*` throttle scopes all live in this settings file but are consumed by `accounts`.
- `analyses` — `AnalysisCreateRateThrottle` (`analysis_create` scope); `Analysis.status` values consumed by `AdminAnalysisListView`/`AdminStatsView`.
- `ai` — `AIRateThrottle` (`ai` scope); `AI_REQUEST_TIMEOUT_SECONDS` and the gunicorn `--timeout 120` sizing are coupled to the AI fallback chain's worst case.
