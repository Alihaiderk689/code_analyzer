# GitHub Integration

## Overview
A GitHub OAuth App (not a GitHub App) lets a user connect their GitHub account and pick one repository to monitor at a time. Once monitored, a real webhook on that repo drives an async pipeline: every PR open/reopen/sync/edit is acknowledged in under a second, queued to Celery, analyzed with the project's existing quality/security/performance engines, and posted back to the PR as a single scored review. The same repo can also be browsed and analyzed on demand from the frontend (file tree, raw file content, single-file/"with context" AI checks), separate from the automatic PR pipeline.

## How it works

### OAuth connect flow (repo access)
1. Frontend calls `GET /api/github/login/` (JWT-authenticated) → `GitHubOAuthService.build_authorize_url(user)` signs `{'purpose': 'link', 'user_id': user.id}` into `state` via Django's `signing` framework (salt `github-oauth-state`, 10 min max age) and returns GitHub's authorize URL (`DEFAULT_OAUTH_SCOPE = 'repo admin:repo_hook read:user user:email'`). Frontend does `window.location = authorize_url`.
2. GitHub redirects the bare browser to `GET /api/github/callback/` (`AllowAny`, no auth classes — a top-level navigation can't carry a JWT). `GitHubCallbackView` decodes `state`'s `purpose` (`peek_state_purpose`, non-raising) to pick which frontend page to redirect to on error, then `GitHubOAuthService().complete_oauth(code, state)`: resolves the user from `state`, exchanges `code` for an access token (`GitHubClient.exchange_code_for_token`), fetches the GitHub profile, `update_or_create`s the `GitHubIntegration`, and calls `integration.set_access_token(raw_token)` → Fernet-encrypts it via `encrypt_token()` before saving.
3. Always ends in an HTTP redirect back into the SPA (`/github?connected=true` or `/github?error=...`), never a raw JSON response.
4. **A second, unrelated flow shares the same callback**: `purpose=login` is GitHub-as-identity-provider for platform login/signup (`accounts.github_auth.find_or_create_user_from_github`, narrower scope `read:user user:email`, nonce-bound via a short-lived cookie to prevent OAuth login-CSRF). It never touches `GitHubIntegration` — see "Related features" below for how the two are distinguished.

### Webhook-driven PR review (end-to-end)
1. GitHub POSTs to `POST /api/webhooks/github/` (`AllowAny`). `GitHubWebhookView` reads `X-GitHub-Event`, `X-GitHub-Delivery`, `X-Hub-Signature-256` headers and the **raw** `request.body` (not `request.data` — signature is computed over exact bytes).
2. `WebhookService.receive()`: `verify_signature()` (HMAC-SHA256 over the raw body with the shared `GITHUB_WEBHOOK_SECRET`, `hmac.compare_digest`) → raises `WebhookVerificationError` → view returns 401. On success, persists a `WebhookEvent` row inside a nested `transaction.atomic()` savepoint; a duplicate `delivery_id` hits the unique constraint and is treated as an idempotent re-delivery (`should_process=False`). `_should_process()` then filters: for `pull_request` events, only `HANDLED_PR_ACTIONS = {opened, reopened, synchronize, edited}` on a currently-monitored (`is_active=True`) repo; for `push`, only non-deleted pushes to the repo's own default branch.
3. View responds **202 immediately** regardless — GitHub only waits seconds and retries on timeout, so nothing beyond signature verification + a DB write happens inline. If `should_process`, `process_pull_request_webhook.delay(event.id)` or `process_push_webhook.delay(event.id)` is queued.
4. `process_pull_request_webhook` (Celery, `bind=True, max_retries=3`): loads the `WebhookEvent`, resolves the still-monitored `GitHubRepository`, `get_or_create`s a `PullRequestAnalysis` keyed on `(repository, pull_request_number, commit_sha)` — a `synchronize` naturally gets a new row via the new SHA; a genuine re-delivery with a different `delivery_id` for an already-`COMPLETED` row is a no-op. Sets status `RUNNING`, then calls `PRAnalysisService().analyze(pr_analysis, access_token)` followed by `CommentService().post_review(...)`.
5. `PRAnalysisService.analyze()`: lists changed files (`GitHubClient.list_pull_request_files`), classifies each (`_classify_file` — skips `removed`/binary/lock-file/generated/unsupported-language/too-large paths), fetches content at the PR's head SHA, runs `_analyze_file_content()` (delegates to `analyses.engine.analyze_code` for quality, `SecurityAnalysisService` for Bandit + custom rules + AI enrichment, plus this app's own `performance_service.find_performance_issues`), and persists one `FileAnalysis` per analyzed file with a normalized `issues` list. Updates `pr_analysis.overall_score` (mean of per-file scores) and `.summary`, marks `COMPLETED`.
6. `CommentService.post_review()`: maps each issue to an inline comment if its line is a valid diff target (`patch_parser.parse_commentable_lines`) and under `MAX_INLINE_COMMENTS=25`, otherwise folds it into the summary body's "Additional findings" list. Posts one `GitHubClient.create_review(event='COMMENT')` call; if GitHub rejects it with inline comments attached, retries summary-only rather than losing the review. Sets `review_posted=True`.
7. Error handling in the task: `GitHubAuthError` (401) marks `integration.token_invalid=True` and fails permanently (not retried — a revoked token won't start working). `GitHubRateLimitError` retries at `exc.reset_at` (or a 60s default) up to `MAX_RETRIES=3`. Other `GitHubAPIError` retries with exponential backoff (30s·2^n). Any other exception is caught broadly and marks the `PullRequestAnalysis`/`WebhookEvent` failed rather than leaving a stuck `RUNNING` row or an unprocessed webhook.
8. `process_push_webhook` just re-queues `build_repository_index.delay(repository.id)` — pushes to the default branch keep the dependency-graph index fresh since GitHub only fires `pull_request` events for PR activity, not plain pushes (no push webhook subscription exists to invalidate it any other way; `RepositoryReindexView` is the manual equivalent).

### Repo/PR/file browsing (frontend-driven, on demand)
- `GitHub.jsx`: `getGitHubStatus()` → connect/disconnect UI; `listGitHubRepositories()` (live GitHub API call, every repo the user has access to, each flagged `is_monitored`) vs. `listMonitoredGitHubRepositories()` (DB-only, "Connected Repositories" section); `selectGitHubRepository`/`deselectGitHubRepository` toggle monitoring. `RepositoryService.select_repository()` enforces **only one repository monitored at a time per integration** — selecting a new one first deselects (and removes the webhook from) whatever was active.
- `GitHubPullRequests.jsx`: hard-scoped to whichever single repo is currently monitored (no cross-repo picker). Pulls `getGitHubMetrics`, `getGitHubQualityTrends` (daily average score, `?days=`, default/max 30/365), and paginated `listGitHubPullRequests` (`PullRequestAnalysisPagination`, page_size 20).
- `GitHubPullRequestDetail.jsx`: `getGitHubPullRequest(id)` → `PullRequestAnalysisDetailSerializer` with every `FileAnalysis`.
- `GitHubRepositoryFiles.jsx`: `getGitHubRepositoryTree` (one full recursive-tree API call, free/unmetered), `getGitHubFileContent` (raw source at HEAD of default branch, free), `getGitHubRepositoryIndexStatus`/`rebuildGitHubRepositoryIndex` (dependency-graph build status, polled every 4s while pending/running), `analyzeGitHubFile` / `analyzeGitHubFileWithContext` (the two quota-gated actions), `getFileCheckQuota`/`getContextCheckQuota`.
- Both analyze endpoints back a "chat about this file" feature: `_create_analysis_for_file_check()` in `repository_views.py` creates a real `Analysis` row (reusing `chat.Conversation`/`ChatMessage` machinery unmodified) linked via `RepositoryFileCheck.analysis`/`RepositoryContextCheck.analysis` (`SET_NULL`, nullable).
- "Analyze with repo context" (`analyze_file_with_context`) additionally fetches the file's direct import-graph neighbors (`_related_paths`, capped `MAX_CONTEXT_RELATED_FILES=3` per relation) and runs each through the same pipeline, bounded by two budgets: `FetchBudget` (`GITHUB_CONTEXT_FETCH_BUDGET_SECONDS`, default 45s) for the GitHub phase, `RequestBudget` (`GITHUB_CONTEXT_REQUEST_BUDGET_SECONDS`, default 90s, `core/execution_budget.py`) for the whole request including the sandboxed runtime check, Bandit, and AI fallback chain. Either exhausting returns a partial result flagged via `context_truncated`/`context_truncated_reason`/`degraded_stages` rather than failing.

### Daily quotas (two, independent)
Both live in `github_integration/services/` and mirror `chat/rate_limit.py`'s pattern exactly: **no counter model** — usage is derived live by counting today's log rows (`RepositoryFileCheck` / `RepositoryContextCheck`), so nothing can drift out of sync with a separate counter.
- `file_check_rate_limit.get_file_check_status()` — `DAILY_FILE_CHECK_LIMIT = 1`, global per user across every monitored repo (not per-repo — matches the one-repo-monitored-at-a-time model). Backs `RepositoryFileAnalyzeView` (`POST /api/github/repositories/<pk>/analyze-file/`).
- `context_check_rate_limit.get_context_check_status()` — `DAILY_CONTEXT_CHECK_LIMIT = 1`, tracked completely separately since a context check costs several fetches + up to one Groq call per related file. Backs `RepositoryFileContextAnalyzeView` (`.../analyze-file-context/`).
- Both reset at the **user's own local midnight**, computed from a client-supplied `tz_offset_minutes` (`Date.getTimezoneOffset()` convention, clamped to real-world UTC-12..+14) — not server time, not a rolling 24h window.
- Re-requesting the *exact same path* already checked today is free (returns the cached stored result, `cached: true`, no new GitHub/Groq call); requesting a *different* path once the day's one check is used returns 429. Files that classify as skip-eligible (binary/lock/generated/unsupported-language/too-large) never consume the quota at all, checked before the quota gate.

### Structured logging
`github_integration` uses `extra={...}` structured logging (per `core/logging_formatters.py`'s `StructuredFormatter`) extensively and consistently: OAuth (`github_oauth.*` in `oauth_service.py`/`oauth_views.py`), webhook receipt/dedup (`github_webhook.*` in `webhook_service.py`), Celery task outcomes (`github_task.*` in `tasks.py`), PR analysis/comment posting (`github_pr_analysis.*`, `github_comment.*`), repo selection/indexing (`github_repository.*`, `repository_index.*`), and the context-check budget/truncation events (`github_context_check.*`). Note the recurring `'created'` collision: `extra={'created': ...}` raises `KeyError` in `logging.Logger.makeRecord()` because `created` is already a built-in `LogRecord` attribute — call sites here use `newly_created` instead.

## Gotchas / non-obvious behavior
- Webhooks must be ack'd within seconds (GitHub retries on timeout) — the view does signature verify + one DB insert, nothing else; all real work (fetch/analyze/comment) is queued to Celery, never inline.
- `GITHUB_TOKEN_ENCRYPTION_KEY`/`GITHUB_CLIENT_ID`/`GITHUB_CLIENT_SECRET`/`GITHUB_WEBHOOK_SECRET` are all validated **lazily**, on first use, not at Django startup — the app boots and runs fine with GitHub unconfigured; affected endpoints return a clear 503/`ImproperlyConfigured` instead.
- Access tokens are Fernet-encrypted at rest (`GitHubIntegration.access_token` is a `BinaryField`); always go through `set_access_token()`/`get_access_token()`, never touch the field directly. Key rotation is explicitly **not supported** today — rotating `GITHUB_TOKEN_ENCRYPTION_KEY` makes every stored token permanently undecryptable (`TokenDecryptionError`), degrading to "affected users reconnect" rather than data loss (tracked as a backlog item in `docs/SECURITY.md`).
- `GITHUB_OAUTH_REDIRECT_URI` must exactly match a callback URL registered on the GitHub OAuth App, and in Docker Compose it must go through nginx, not a bare backend port — the backend container publishes no port to the host at all.
- Only **one repository can be monitored per integration at a time** — selecting a new repo silently deselects (and removes the webhook from) whatever was previously monitored; this is why `GitHubPullRequests.jsx` and the quota systems are "global per user," not per-repo.
- `PullRequestAnalysis`'s uniqueness is `(repository, pull_request_number, commit_sha)` — the real defense against duplicate webhook processing; `WebhookEvent.delivery_id` uniqueness is only the transport-level first line of defense (a genuine GitHub re-delivery can arrive with a different `delivery_id` for the same logical event).
- A `GitHubAuthError` (401 from GitHub) is treated as non-retryable everywhere it's caught (both `process_pull_request_webhook` and `build_repository_index`) — it flips `integration.token_invalid=True` so the frontend can prompt reconnect instead of Celery retrying forever against a token that will never work.
- There is no push webhook subscription that invalidates the dependency-graph index automatically beyond the default branch — `RepositoryIndex` is rebuilt on `select_repository`, on every push to the default branch (`process_push_webhook`), and manually via `RepositoryReindexView`; it can otherwise go stale.
- The daily file-check and context-check quotas reset at **the user's own local midnight** (client-reported UTC offset), not server time or a rolling window — same non-obvious semantics as `chat/rate_limit.py`.
- Browsing (file tree, raw file content) is always free/unmetered; only the two "Analyze" actions consume quota — and even those are free again for the exact same path already checked today.
- The callback view (`GitHubCallbackView`) serves two unrelated flows (`purpose=link` repo-connect vs. `purpose=login` sign-in) through one URL because a GitHub OAuth App only supports a single registered callback — disambiguated via the signed `state` payload, never via request auth state.
- `PRAnalysisService`/`SecurityAnalysisService` never reimplement quality/security analysis — they orchestrate the *existing* `analyses.engine` and `analyses.services.security_service` pipelines; only performance-smell detection (`performance_service.py`) is unique to this app, since no performance category exists elsewhere in the project.

## Related features
- **auth-accounts / accounts app**: GitHub is also used as a *login/signup* identity provider (`accounts.github_auth.find_or_create_user_from_github`, `GET /api/auth/github/` → `getGithubAuthLoginUrl()` in `resources.js`), reusing the same OAuth App/callback but a completely separate concern from `GitHubIntegration` (repo access) — distinguished via `state`'s `purpose` field (`link` vs `login`) and a browser-bound nonce cookie (`GITHUB_LOGIN_NONCE_COOKIE`, `accounts/cookies.py`) to prevent OAuth login-CSRF. `complete_login_oauth` never touches `GitHubIntegration`.
- **analyses**: `PRAnalysisService` and the on-demand file-check views call directly into `analyses.engine.analyze_code`, `analyses.services.security_service.SecurityAnalysisService`, `bandit_service.py`, `custom_rules_service.py`, `ai_security_service.py`, and reuse `Analysis`/`analyses.models` for the "chat about this file" linkage.
- **chat**: on-demand file checks create a real `Analysis` row specifically so the existing `chat.Conversation`/`ChatMessage` UI and 3-messages/day quota work unmodified for GitHub-sourced files; `file_check_rate_limit.py`/`context_check_rate_limit.py` mirror `chat/rate_limit.py`'s local-midnight quota pattern exactly.
- **ai (ai/client.py)**: indirectly used via `AISecurityService` (security finding enrichment) during PR review and on-demand checks — not a direct call site itself, but shares the same "AI unavailable" failure handling philosophy.
- **infra-cross-cutting**: structured `extra={...}` logging (`core/logging_formatters.py`), the two independent rate-limiting mechanisms described in `CLAUDE.md` (this app uses the daily-quota style, not DRF throttle scopes), and `core/execution_budget.py`'s shared request-budget abstraction (also usable outside this app).
