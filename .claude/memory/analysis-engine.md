# Analysis Engine & Sandbox

## Overview
This is the base "paste/upload code, get back an `Analysis` with issues and a quality score" pipeline — not security scanning, not AI suggestions, not GitHub PR review (those are separate features layered on top of the same `Analysis` model). It is a two-part design: `analyses/engine.py` does language-agnostic static analysis (plus real `ast`/`pyflakes`-based checks for Python), and `analyses/sandbox.py` optionally runs submitted Python inside a macOS Seatbelt (`sandbox-exec`) sandbox to catch runtime errors static analysis can't predict. Everything runs synchronously inside the request/response cycle — there is no Celery task involved in this particular flow (unlike GitHub PR review).

## Key files
- `backend/analyses/models.py` — the `Analysis` model: status enum, `issues` JSONField, `quality_score`, `security_report` (different feature), `repo_context` (GitHub-only).
- `backend/analyses/engine.py` — `analyze_code()`: textual checks (TODO/long-line/no-comments), Python `ast`/`pyflakes` checks, `ISSUE_PENALTIES`, `_score()`, language detection.
- `backend/analyses/sandbox.py` — `is_available()`, `run_python()`, the Seatbelt profile (`_build_profile`), traceback parsing.
- `backend/analyses/analysis_views.py` — `_run_analysis()` orchestration, `AnalyzeView`, `UploadView`, `AnalysisListView`, `AnalysisDetailView`, `ReanalyzeView`, `CancelView`, `StatusView`, `ClearHistoryView`.
- `backend/analyses/analysis_urls.py` — routes mounted at `api/analysis/` in `config/urls.py` (note: `analyses/urls.py` is actually the *dashboard* routes, mounted at `api/dashboard/` — don't confuse the two).
- `backend/analyses/serializers.py` — `AnalysisSerializer` (list), `AnalysisDetailSerializer` (includes `issues`), `AnalysisStatusSerializer`, `AnalyzeRequestSerializer`, `UploadRequestSerializer`.
- `backend/core/throttling.py` — `AnalysisCreateRateThrottle` (scope `analysis_create`), applied to `AnalyzeView`/`UploadView`/`ReanalyzeView`.
- `backend/core/execution_budget.py` — `ExecutionBudget`/`RequestBudget`, `STAGE_RUNTIME_CHECK`; optional shared deadline (only used by the GitHub repo-context path, not plain paste/upload — `budget=None` everywhere else).
- `frontend/src/pages/NewAnalysis.jsx` — paste/upload submission UI, caches source in `sessionStorage` for the Report page's diff/source views (backend never returns `source_code`).
- `frontend/src/pages/Report.jsx` — renders quality score, LOC, issue count, status; reanalyze/delete/PDF/HTML export actions.
- `frontend/src/components/AnalysisTabs.jsx` — Issues/Source/AI Suggestions/AI Explanation/Refactored Code tabs; `IssuesTab` branches on whether `issue.severity` is present to decide plain-list vs. grouped rendering.
- `frontend/src/components/IssueGroups.jsx` — groups issues by `source` (`security`/`performance`/general) — this shape comes from a *different* pipeline (PR/file-check `pr_analysis_service`), not `engine.py`'s plain issues.
- `frontend/src/pages/History.jsx` — list/search/delete/clear-all, backed by `listHistory`/`searchAnalyses`/`clearHistory`.
- `frontend/src/lib/resources.js` — `submitAnalysis`, `uploadAnalysis`, `getAnalysis`, `deleteAnalysis`, `reanalyzeAnalysis`.

## How it works
**Submission.** `AnalyzeView.post` (paste) validates via `AnalyzeRequestSerializer` (non-empty after `.strip()`, ≤200,000 chars), creates an `Analysis` row with `status=PENDING`, `language=detect_language_from_code(code)` (regex-signature scoring across Python/TypeScript/JavaScript/Java/C++/Go/PHP, plus a weak "does it parse as Python" bonus; returns `'Unknown'` if nothing scores). `UploadView.post` validates via `UploadRequestSerializer` (≤2MB), decodes as UTF-8 (400 if it fails, no row created), rejects whitespace-only content (400, no row created), detects language from the filename extension (`detect_language`/`LANGUAGE_BY_EXTENSION`) instead of content-sniffing.

**Orchestration.** Both views call `_run_analysis(analysis)` synchronously in the same request. It calls `engine.analyze_code(analysis.source_code, analysis.language)`, and on success sets `lines_of_code`, `issues`, `issues_count`, `quality_score`, `status=COMPLETED`, and saves. On *any* unexpected exception from the engine (not just sandbox mishaps — anything `engine.py`/`sandbox.py` didn't already anticipate), it logs (`logger.exception('analysis_run_failed', extra={'analysis_id': ...})`) and sets `status=FAILED`, saving only `['status', 'updated_at']`. Because this all happens inline before the HTTP response is returned, a client only ever observes `COMPLETED` or `FAILED` from a fresh `analyze`/`upload`/`reanalyze` call — `PENDING`/`RUNNING` are set transiently but not really "polled" for this flow (contrast with GitHub PR review, which is async via Celery).

**engine.analyze_code(code, language, budget=None).** Steps:
1. `lines_of_code` = count of non-blank lines.
2. Line-by-line textual checks: `TODO_PATTERN` (`TODO|FIXME|HACK|XXX`, case-insensitive) → `todo` issue; `len(line) > MAX_LINE_LENGTH` (120) → `long_line`; lines starting with `COMMENT_PREFIXES` (`#`, `//`, `/*`, `*`, `--`) counted toward `comment_lines`.
3. If `lines_of_code >= 30 and comment_lines == 0` → one `no_comments` issue (line `None`).
4. If `language == 'Python'`, extends `issues` with `_python_issues(code, budget)`.
5. `quality_score = _score(lines_of_code, issues)`.

**Python-specific checks (`_python_issues`).** First tries `ast.parse(code)`. On `SyntaxError`, falls back to `parso` with `error_recovery=True` so *every* syntax error in the file is reported in one pass (ast.parse stops at the first one) — `_dedupe_cascading_syntax_errors` strips the spurious "unexpected indent" parso reports on the line right after a real error. When there's a syntax error, undefined-name/unused-import checks and the sandbox are both skipped entirely (function returns early). Otherwise runs `pyflakes.checker.Checker(tree).messages`, mapping each message's class name to an issue type via `_PYFLAKES_TYPE_OVERRIDES` (or `_camel_to_snake` fallback) — types include `undefined_name`, `undefined_export`, `duplicate_argument`, `import_star_used`, `redefined_while_unused`, `unused_variable`, `unused_import`. Then appends `_python_runtime_issues(code, budget)` — only reached once the code is known to at least parse cleanly.

**Quality score (`_score`).** Returns `0.0` if `lines_of_code == 0`. Otherwise `penalty = sum(ISSUE_PENALTIES.get(issue['type'], 2) for issue in issues)` (unknown issue types default to a penalty of 2) and `quality_score = round(max(0.0, 100.0 - penalty), 1)` — floors at 0, never negative. `ISSUE_PENALTIES`: `todo=3`, `long_line=1`, `no_comments=5`, `syntax_error=40`, `undefined_name=15`, `undefined_export=10`, `duplicate_argument=10`, `import_star_used=5`, `redefined_while_unused=5`, `unused_variable=2`, `unused_import=2`, `runtime_error=50`, `execution_timeout=30`, `runtime_check_unavailable=0`, `runtime_check_skipped=0`.

**Sandbox (Python only, `sandbox.run_python`).** `_python_runtime_issues` first checks `budget.can_afford(sandbox.TIMEOUT_SECONDS, STAGE_RUNTIME_CHECK)` if a budget was passed (it's `None` for plain paste/upload, so this unconditionally runs for that flow) — if unaffordable, emits `runtime_check_skipped` (penalty 0) instead of running. Then calls `sandbox.run_python(code)`:
- `is_available()` — `True` only if `sandbox-exec` is on `PATH` *and* `/usr/bin/python3` exists. Non-macOS hosts (e.g. Linux prod) always get `{'status': 'unavailable'}`, surfaced as issue type `runtime_check_unavailable` with an explicit user-facing message ("Runtime error detection is unavailable on this server (requires macOS)") — **not** silent degradation.
- When available: writes `code` to a scratch dir's `submission.py`, builds a Seatbelt profile (`_build_profile`) denying-by-default with exceptions for: `process-exec`/`process-fork` (unrestricted — narrowing to a literal Python path broke macOS's Xcode-stub re-exec), all file reads *except* the project root (`PROJECT_ROOT = Path(__file__).resolve().parent.parent`, i.e. `backend/`) and the invoking user's home dir (`HOME_DIR`), read+write confined to the resolved-realpath scratch dir, all network denied, plus metadata/sysctl-read/mach-lookup/iokit-open allowances needed for a normal Python interpreter to start. `stdin=subprocess.DEVNULL` so `input()` raises `EOFError` immediately. `resource.setrlimit` caps `RLIMIT_CPU` (5s), `RLIMIT_NPROC` (16), `RLIMIT_CORE` (0), `RLIMIT_FSIZE` (10MB) — memory limits (`RLIMIT_AS`/`RLIMIT_DATA`) cannot be lowered on macOS at all, so the wall-clock `TIMEOUT_SECONDS=5` (via `subprocess.run(..., timeout=...)`) is the real backstop, not a memory cap.
- Return shapes: `{'status': 'ok'}` (clean exit), `{'status': 'error', 'exception_type', 'message', 'line'}` (uncaught exception, parsed from stderr traceback via `_parse_traceback` — becomes `runtime_error`, penalty 50), `{'status': 'import_error', ...}` (sandbox's bare system Python lacks the real code's third-party deps — deliberately **not** reported as a bug, engine.py drops it silently), `{'status': 'timeout'}` (→ `execution_timeout`, penalty 30, "possible infinite loop"), `{'status': 'unavailable'}` (→ `runtime_check_unavailable`, penalty 0).
- Only the *first* uncaught runtime error surfaces per analysis (same as running the script yourself).

**Status state machine.** `Analysis.Status`: `PENDING`, `RUNNING`, `COMPLETED`, `FAILED`, `CANCELLED`. In practice for this flow, a row goes `PENDING` (at `.objects.create`) → `COMPLETED`/`FAILED` within the same synchronous request via `_run_analysis` — `RUNNING` is not actually set anywhere in this file's code path (no code sets it to `RUNNING`); it exists in the enum but is effectively vestigial for the base flow. `CancelView` only permits cancelling from `PENDING`/`RUNNING`, but since analysis completes synchronously before the response returns, there's essentially no window for a concurrent cancel request to land — cancel is realistically dead code for this feature (it may matter more for other flows that reuse the same model, e.g. GitHub on-demand file checks).

**CRUD/list endpoints**, all owner-scoped via `get_object_or_404(Analysis, pk=pk, owner=request.user)` or `Analysis.objects.filter(owner=request.user)`: `AnalysisListView` (GET list, uses lightweight `AnalysisSerializer` without `issues`), `AnalysisDetailView` (GET full detail incl. `issues`, DELETE), `ReanalyzeView` (POST — re-runs `_run_analysis` against the stored `source_code`; 400 if `source_code` is blank), `CancelView`, `StatusView` (GET — minimal polling shape), `ClearHistoryView` (DELETE all of the owner's analyses).

**Throttling.** `AnalyzeView`, `UploadView`, `ReanalyzeView` all set `throttle_classes = [AnalysisCreateRateThrottle]` (scope `analysis_create`, rate configured in `settings.DEFAULT_THROTTLE_RATES`), keyed by user id (all these endpoints require auth). `AnalysisListView`/`AnalysisDetailView`/`CancelView`/`StatusView`/`ClearHistoryView` have no extra throttle beyond the blanket `UserRateThrottle`.

**Frontend flow.** `NewAnalysis.jsx`: paste (textarea + synced line-number gutter) or drag-and-drop/file-picker upload; calls `submitAnalysis`/`uploadAnalysis` from `resources.js`, which POST to `/analysis/analyze/` / `/analysis/upload/`. On success, stashes the raw source in `sessionStorage` under `ca_source_${result.id}` (the backend's `AnalysisDetailSerializer` never returns `source_code`, so this is the *only* place the original text is ever available client-side) and navigates to `/report/:id`. `Report.jsx` fetches via `getAnalysis(id)`, renders `MetricCard`s for quality score / LOC / issues found / status, and hosts `AnalysisTabs`. `AnalysisTabs.jsx`'s `IssuesTab` inspects `issues[0].severity` to decide whether to render plain `engine.py`-shaped issues (dot + message + type label + line) or the grouped `IssueGroups.jsx` rendering (used by the different PR/file-check pipeline, which has `severity`/`source`/`explanation`/`remediation` fields engine.py issues don't have). `History.jsx` lists/searches/deletes via `listHistory`/`searchAnalyses`/`clearHistory`.

## Gotchas / non-obvious behavior
- **Sandbox is macOS-only and self-disclosing, not silently degraded.** `sandbox.is_available()` gates everything; on Linux (real prod hosts) `runtime_error`/`execution_timeout` checks simply never run, and the user is told via a zero-penalty `runtime_check_unavailable` issue rather than the app pretending the code was fully vetted.
- **`runtime_check_unavailable` and `runtime_check_skipped` both carry penalty 0 by design** — not running a check is not evidence of a problem; don't "fix" `ISSUE_PENALTIES` to penalize these.
- **`import_error` from the sandbox is dropped, not reported.** The sandbox runs a bare system Python with none of the real project's third-party dependencies, so a `ModuleNotFoundError`/`ImportError` there says nothing about code correctness.
- **A syntax error short-circuits everything else Python-specific** — no pyflakes checks, no sandbox run — because `_python_issues` returns immediately after the parso-based syntax-error list.
- **`_run_analysis` catches *any* exception from `analyze_code`**, not just anticipated ones, and always marks `FAILED` rather than leaving a row stuck in `PENDING`/`RUNNING` — this is a deliberate belt-and-suspenders on top of `engine.py`/`sandbox.py`'s own defensive returns.
- **`RUNNING` status is essentially unused** in this flow's actual code path — everything happens synchronously within one request, so a fetched `Analysis` is always seen in `PENDING` (very briefly, pre-save) or a terminal state. `CancelView` exists but has no realistic window to fire against this flow.
- **Unknown issue types default to penalty 2** in `_score`, not 0 — a bug that emits an issue with a typo'd/new `type` still silently dents the score.
- **Source code is never returned to the client after creation.** `AnalysisDetailSerializer`/`AnalysisSerializer` don't include `source_code` at all; the frontend's only copy lives in `sessionStorage` from the moment of submission, which is why Report.jsx's Source/Refactor-diff tabs show "not available for this session" after a page reload or in a different browser tab.
- **`detect_language` (upload, filename-based) and `detect_language_from_code` (paste, content-based) are different functions** with different failure modes — upload trusts the extension even if the content doesn't match; paste can return `'Unknown'` and then skips all Python-specific checks (`engine.analyze_code` only runs `_python_issues` when `language == 'Python'` exactly).
- **`budget` is `None` for this entire feature** (plain paste/upload/reanalyze) — the `ExecutionBudget`/`can_afford` machinery in `core/execution_budget.py` only activates for the GitHub repository-context analysis path, which is a different feature layered on the same `engine.py` function.
- **`analyses/urls.py` is the dashboard routes** (`api/dashboard/...`), while the analysis CRUD routes documented here live in `analyses/analysis_urls.py` (`api/analysis/...`) — easy to grab the wrong file by name.

## Related features
- **security-scanning** (`analyses/security_views.py`, `analyses/services/`) — separate pipeline (Bandit + custom rules + AI enrichment), cached in the same `Analysis.security_report` field, not mixed into `issues`/`quality_score`.
- **ai-suggestions/chat** (`analyses/ai_views.py`, `chat/`) — AI suggestions/explanation/refactor and persisted chat operate on a completed `Analysis`'s stored `issues`/`source_code`; both catch AI-call failures the same way (503).
- **github-integration** (`github_integration/`) — PR review and on-demand file checks create `Analysis` rows too (`_create_analysis_for_file_check`), reusing `AnalysisTabs`/the generic `/analysis/<id>/...` AI endpoints, but their issues carry `severity`/`source` fields this engine's plain issues don't (see `IssueGroups.jsx` vs. the plain list in `AnalysisTabs.jsx`).
- **reports** (`analyses/report_views.py`) — PDF/HTML export of a completed `Analysis`.
- **frontend-app** — `NewAnalysis.jsx`/`Report.jsx`/`History.jsx`/`AnalysisTabs.jsx` as documented above.
