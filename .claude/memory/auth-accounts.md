# Auth & Accounts

## Overview
Covers everything in `backend/accounts/` plus the frontend auth surface: registration with email OTP verification, email/password login, Google and GitHub social login, password reset, per-endpoint throttling, and user profile/settings management. The core design decision is httpOnly-cookie JWT auth with a CSRF double-submit check layered on top, because frontend (`:5173`) and backend (`:8000`) are separate origins even in dev — frontend JS never touches the raw access/refresh tokens, only a JS-readable `csrftoken` cookie it echoes back as a header on unsafe requests.

## Key files
- `backend/accounts/models.py` — `Profile` (one-to-one with `User`; verification flag, avatar, `google_id`/`github_id`, OTP fields) and `PendingRegistration` (holds unverified signups so a User row is only created once an OTP is proven).
- `backend/accounts/views.py` — all auth/account endpoints: `CsrfCookieView`, `RegisterView`, `LoginView`, `GoogleLoginView`, `GitHubLoginInitiateView`, `RefreshView`, `LogoutView`, `ForgotPasswordView`, `ResetPasswordView`, `VerifyOtpView`, `ResendVerificationView`, `ChangePasswordView`, `ProfileView`, `AvatarUploadView`.
- `backend/accounts/serializers.py` — `RegisterSerializer`, `EmailLoginSerializer`, `GoogleLoginSerializer`, `ChangePasswordSerializer`, `ForgotPasswordSerializer`, `ResendVerificationSerializer`, `VerifyOtpSerializer`, `ResetPasswordSerializer`, `ProfileSerializer`, `DeleteAccountSerializer`, `AvatarUploadSerializer`; also `_generate_username()` and `create_verified_user()`.
- `backend/accounts/authentication.py` — `CookieJWTAuthentication`, the sole `DEFAULT_AUTHENTICATION_CLASSES` entry: header-or-cookie token source, CSRF enforced only for cookie-sourced auth.
- `backend/accounts/cookies.py` — single source of truth for cookie names/flags: `ACCESS_COOKIE`, `REFRESH_COOKIE` (path-scoped to `/api/auth/`), `GITHUB_LOGIN_NONCE_COOKIE`; `set_auth_cookies()`/`clear_auth_cookies()`/`set_github_login_nonce_cookie()`/`clear_github_login_nonce_cookie()`.
- `backend/accounts/otp.py` — OTP generation/hashing/verification/lockout (`issue_otp`/`issue_otp_to`, `verify_otp`, `consume_pending_registration`), HMAC-peppered hash, row-locking against concurrent guesses.
- `backend/accounts/validators.py` — DRF field validators: `validate_password_strength`, `validate_username_format`, `validate_person_name`, `validate_otp_code`, `normalize_email`.
- `backend/accounts/password_validation.py` — `PwnedPasswordsValidator`, wraps `pwned_passwords_django` with an on/off switch (`settings.PWNED_PASSWORDS_ENABLED`, off during tests).
- `backend/accounts/tokens.py` — `revoke_all_refresh_tokens(user)`, blacklists every outstanding refresh token (simplejwt token_blacklist app).
- `backend/accounts/google_auth.py` — `verify_google_access_token()`, verifies the classic OAuth-popup access token against Google's `tokeninfo`+`userinfo` endpoints (not ID-token JWT verification).
- `backend/accounts/github_auth.py` — `find_or_create_user_from_github()`, the account-linking half of GitHub login (separate from `github_integration`, the repo-analysis app).
- `backend/accounts/emails.py` / `brevo_client.py` — OTP and password-reset emails sent via Brevo's transactional API, not Django mail backends.
- `backend/accounts/signals.py` — `post_save` on `User` auto-creates the `Profile` row.
- `backend/accounts/urls.py` (mounted under `/api/auth/`) and `profile_urls.py` (mounted under `/api/users/`).
- `backend/github_integration/oauth_views.py` — `GitHubLoginView`/`GitHubCallbackView`/`GitHubDisconnectView`/`GitHubIntegrationStatusView`. **`GitHubCallbackView` is shared** between the login flow (`purpose=login`, unauthenticated) and the "connect a repo" integration flow (`purpose=link`, authenticated) — one GitHub OAuth App only supports one callback URL; the two are disambiguated via the signed `state` payload (`GitHubOAuthService.peek_state_purpose`), never via request auth state.
- `backend/config/settings.py` — `AUTH_COOKIE_SECURE`/`AUTH_COOKIE_SAMESITE`, `SIMPLE_JWT`, `CORS_ALLOWED_ORIGINS`/`CORS_ALLOW_CREDENTIALS`/`CSRF_TRUSTED_ORIGINS`/`CSRF_COOKIE_DOMAIN`, `_THROTTLE_RATES`, `REST_FRAMEWORK['DEFAULT_AUTHENTICATION_CLASSES']`, `AUTH_PASSWORD_VALIDATORS`, `GOOGLE_CLIENT_ID`.
- `backend/core/throttling.py` — `LoginRateThrottle`, `RegisterRateThrottle`, `PasswordResetRateThrottle`, `OtpVerifyRateThrottle`, `OtpVerifyAccountRateThrottle`, `OtpResendRateThrottle` (all `ScopedIdentityRateThrottle` subclasses, not DRF's `ScopedRateThrottle`).
- `frontend/src/lib/api.js` — `apiFetch()`, `primeCsrf()`, `csrfHeaders()`, `refreshAccessToken()` (401-triggered, single in-flight promise), `ApiError`.
- `frontend/src/lib/AuthContext.jsx` — `AuthProvider`/`useAuth()`: session restore on boot, `login`/`loginWithGoogle`/`logout`/`refreshUser`, `checkIsAdmin()` (probes an admin-only endpoint since the profile response never carries `is_staff`).
- `frontend/src/lib/resources.js` — auth/account endpoint wrappers (`registerUser`, `loginUser`, `googleLogin`, `getGithubAuthLoginUrl`, `logoutUser`, `requestPasswordReset`, `resetPassword`, `verifyOtp`, `resendVerification`, `fetchProfile`, `updateProfile`, `changePassword`, `deleteAccount`, `uploadAvatar`).
- `frontend/src/lib/validation.js` — client-side mirror of `backend/accounts/validators.py` (name/username/email/password/OTP rules).
- `frontend/src/pages/Login.jsx`, `Register.jsx`, `ResetPassword.jsx`, `VerifyEmail.jsx`, `Settings.jsx` — the corresponding screens.

## How it works

**Registration** (`RegisterView` → `RegisterSerializer`): No `User` row is created at this step. A `PendingRegistration` row is created/replaced (`update_or_create` keyed by email — a re-submit for an unverified address just re-issues the code, it isn't a conflict), storing the already-hashed password. An address only counts as "taken" if an existing `User` is `is_active` or `profile.is_verified` (`validate_email`); a stranded inactive/unverified `User` from the old pre-`PendingRegistration` flow is deleted so the address becomes claimable again. `issue_otp_to()` + `send_otp_email_to()` run inside the same `transaction.atomic()` as the `PendingRegistration.save()`, so a Brevo failure (`BrevoAPIError` → 503) rolls back the pending row too, rather than leaving a code nobody received.

**Email verification** (`VerifyOtpView` → `VerifyOtpSerializer` → `accounts/otp.py`): looks up `PendingRegistration` first (signup case); if found, `consume_pending_registration()` locks the row (`select_for_update`), checks the code, calls `create_verified_user()` (materializes the `User` with the pre-hashed password, `profile.is_verified = True`) inside the same transaction, then deletes the pending row. If no pending row exists, falls back to an existing `User.profile` (email-change or legacy-account case) via `verify_otp()`, which locks the `Profile` row, activates the user (`is_active = True`), and clears the OTP fields. Both paths use `_check_locked()`: expired / too-many-attempts (`OTP_MAX_ATTEMPTS = 5`) / incorrect, with wrong guesses persisting an incremented `otp_attempts` — row-locking exists specifically so concurrent parallel guesses can't each cost less than one real attempt. Resend (`ResendVerificationView`) re-issues into the same fields via `issue_otp_to`/`issue_otp`.

**Login** (`LoginView(TokenObtainPairView)` + `EmailLoginSerializer`): unknown email and wrong password deliberately share one error message (anti-enumeration); an inactive-and-unverified account gets a distinct "not verified yet" message since the caller already proved they hold the password. On success the view pops `access`/`refresh` out of the JSON body and calls `set_auth_cookies()` — the tokens never reach the response body the frontend sees.

**Google login** (`GoogleLoginView` + `GoogleLoginSerializer`): frontend uses the classic OAuth *popup* flow (`@react-oauth/google`'s `useGoogleLogin`, implicit flow — access token, not ID token) specifically to avoid Google Identity Services' auto-select "Sign in as X" UX. `google_auth.verify_google_access_token()` does two REST calls to Google (`tokeninfo` for the audience check, `userinfo` for profile claims) rather than local JWT verification. Find-or-create: matches on `profile.google_id` first; on first sight of a Google sub, only auto-links/creates if Google reports `email_verified`; auto-linking an existing email-matched account is blocked if that account already has a *different* `google_id` linked (`GitHubAccountConflictError`-equivalent inline `ValidationError`).

**GitHub login** (`GitHubLoginInitiateView` + `github_integration/oauth_views.GitHubCallbackView._complete_login`): no client-side shortcut like Google's, so it's a full redirect. `GitHubLoginInitiateView` (`GET /api/auth/github/`) returns an authorize URL and sets a `GITHUB_LOGIN_NONCE_COOKIE` (httpOnly, `SameSite=Lax` always, 10 min, path `/api/`) binding the flow to this browser — verified against the `state` nonce in the callback to prevent OAuth login-CSRF (an attacker completing their own authorize step and handing the resulting code+state to a victim). The callback view is **shared** with the "connect a repo" integration flow; `state`'s signed `purpose` field decides which branch runs, not request auth state. `find_or_create_user_from_github()` in `accounts/github_auth.py` mirrors Google's find-or-create logic but requires GitHub to report a verified primary email; on success issues tokens and cookie-redirects to `/admin` (staff) or `/dashboard`, error cases redirect to `/login?error=...`. The nonce cookie is cleared unconditionally on every callback outcome (single-use).

**Token refresh** (`RefreshView`): reads `refresh_token` only from its httpOnly cookie — the request body is never consulted, by design, since the frontend never has the raw token to send. Reuses simplejwt's `TokenRefreshSerializer` for rotation/blacklist-after-rotation behavior (`SIMPLE_JWT['ROTATE_REFRESH_TOKENS']`/`BLACKLIST_AFTER_ROTATION'] = True`). On `TokenError` it 401s and clears both cookies.

**Logout** (`LogoutView`): always returns success and clears cookies, whether or not there was a valid refresh token to blacklist — an already-missing/expired/replayed cookie shouldn't produce a confusing error for a user whose actual goal ("be logged out") is already satisfied.

**Password reset** (`ForgotPasswordView` + `ResetPasswordView`): forgot-password always returns the same response regardless of whether the email exists (anti-enumeration); uses Django's `default_token_generator` (not the OTP system) with `uid`/`token` query params baked into a link to `{FRONTEND_URL}/reset-password`. `ResetPasswordView` is unauthenticated; on success it calls `revoke_all_refresh_tokens(user)` and does **not** re-issue tokens — the frontend sends the user to `/login` afterward. Reasoning documented in `views.py`: the person resetting may be locked out precisely because someone else is already logged in, so leaving that session's refresh token valid would defeat the reset.

**Change password** (`ChangePasswordView`, authenticated): unlike reset, this *does* revoke-then-reissue — `revoke_all_refresh_tokens(request.user)` then immediately mints and cookie-sets a fresh pair for the calling session, so the browser that just changed the password doesn't get logged out on its next silent refresh.

**CSRF priming/enforcement**: `CsrfCookieView` (`GET /api/auth/csrf/`) calls Django's `get_token(request)`, which makes Django issue the JS-readable `csrftoken` cookie, **and also returns that token in the JSON body** (`{"csrfToken": ...}`). `AuthContext.jsx`'s session-restore effect calls `primeCsrf()` unconditionally on boot, before the profile fetch; `primeCsrf()` reads the body and caches it in an in-memory module variable in `api.js`. `csrfHeaders()` prefers that in-memory value for `X-CSRFToken`, falling back to parsing `document.cookie` only if it's unset. This is deliberate, not redundant: `document.cookie` can only ever see a cookie whose `Domain` is the page's own domain (or a parent domain via `CSRF_COOKIE_DOMAIN`) — a same-origin/subdomain rule, unrelated to `SameSite` (which only governs whether the browser *sends* a cookie, not who can *read* one via JS). When frontend and backend are on genuinely unrelated domains, the browser still sends the cookie back with the request, but frontend JS can never read it to populate the header — every mutating request 403s "CSRF token missing" no matter how `CORS_ALLOWED_ORIGINS`/`COOKIE_DOMAIN` are set. The body-token path sidesteps that: it works regardless of hosting topology. (The body token and cookie token are never byte-identical — Django re-masks the underlying CSRF secret with a new random mask on every `get_token()`/middleware call, purely to avoid a BREACH-style oracle; `CSRFCheck` unmasks both sides before comparing, so either masked encoding of the same secret is accepted. See `CookieAuthCSRFTests.test_unsafe_request_with_body_csrf_token_succeeds` in `backend/accounts/tests.py`.) Enforcement is in `CookieJWTAuthentication._enforce_csrf()`: it only runs when auth came from the cookie, using DRF's `CSRFCheck` reused directly (not Django's full CSRF middleware path); reason string surfaces as a 403 `PermissionDenied`.

**CookieJWTAuthentication cookie-vs-header decision** (`authentication.py`): checks `Authorization: Bearer` header first (non-browser clients — scripts, admin tooling) and returns immediately if present, with **no CSRF check** in that path. Only falls back to the `access_token` cookie — and only then runs `_enforce_csrf()` — when no bearer header was supplied. This is the load-bearing security property: a cookie is attached automatically by the browser (needs CSRF protection), a bearer header is not (another site can't set it).

**Throttle scopes in play**: `login` (10/min), `register` (5/hour), `password_reset` (20/hour, shared by forgot- and reset-password), `otp_verify` (20/hour, IP-keyed backstop), `otp_verify_account` (10/hour, keyed by IP+SHA256(email) — bounds how much of one IP's budget can hit a single target), `otp_resend` (5/hour — real cost per send since it's a live Brevo call). `GitHubLoginInitiateView` also uses `LoginRateThrottle`. All widened to `1000000/day` under `manage.py test` (`_RUNNING_TESTS` in settings.py) since the Django test client reuses one `REMOTE_ADDR` and `LocMemCache` persists for the whole run.

**Profile/settings flow** (`ProfileView`, `AvatarUploadView`): `GET` returns `ProfileSerializer` (id, username, email, first_name, last_name, is_verified, avatar, date_joined). `PATCH` is partial; changing `email` flips `profile.is_verified = False`, sends a fresh OTP, and runs in one `transaction.atomic()` so a Brevo failure rolls back the email change too (mirrors registration's pattern) — `is_active` is untouched, so the user isn't locked out mid-change, just unverified. `DELETE` requires the current password (`DeleteAccountSerializer`) and hard-deletes the `User`. `AvatarUploadView` enforces a 5MB max (`AvatarUploadSerializer.validate_avatar`) and returns an absolute URL via `request.build_absolute_uri`. Frontend: `Register.jsx` stashes `first_name`/`last_name` in `sessionStorage` (keys `ca_pending_first_name`/`ca_pending_last_name`) because there's no account to attach them to until OTP verification; `AuthContext.login()` applies them via `updateProfile()` right after login succeeds, best-effort (failure doesn't block login). `Register.jsx` also stashes the email under `ca_pending_email` since router state doesn't survive a reload of `/verify-email`.

**Frontend 401 handling**: `apiFetch()` does a single automatic refresh-and-retry on a 401 (guarded by the `auth` option, default `true`; auth-flow calls like login/register pass `auth: false` to skip it since a 401 there is a real answer, not an expired session). Concurrent 401s share one in-flight `refreshAccessToken()` promise (`refreshPromise` module-level variable) rather than each firing their own refresh call.

## Gotchas / non-obvious behavior
- `AUTH_COOKIE_SECURE`/`AUTH_COOKIE_SAMESITE` are `False`/`Lax` in dev, `True`/`None` in production (`config/settings.py:125-126`) — `SameSite=None` requires `Secure`, and `Secure` cookies are never sent over plain `http://`, so this pairing is not swappable independently.
- The httpOnly JWT cookies still require `SameSite=None`+`Secure` in production to flow cross-site at all (browser-level, unaffected by domain relatedness). The CSRF *token delivery* no longer depends on frontend/backend sharing a registrable domain — `primeCsrf()` gets the token from the `/auth/csrf/` response body, not `document.cookie` (see above) — but `CSRF_COOKIE_DOMAIN` (from `COOKIE_DOMAIN` env var) still matters if you want the fallback cookie-read path to work too; left unset it's host-only, correct for dev's same-site-different-port setup.
- `primeCsrf()` must run before the *first* mutating request of a session or every POST/PATCH/DELETE 403s "CSRF token missing" — `AuthContext.jsx` calls it unconditionally on boot, before even checking whether a session exists.
- `RefreshView` reads the refresh token from its cookie only, **never** the request body — `test_refresh_ignores_body_and_only_trusts_cookie` in `tests.py` locks this in.
- Bearer-header auth (`Authorization: Bearer ...`) skips CSRF entirely — only cookie-sourced auth enforces it. A script/admin-tool client using a header never needs an `X-CSRFToken`.
- Throttle rates are widened to `1000000/day` for every scope during `manage.py test` (`_RUNNING_TESTS`) — tests that need to exercise real throttling (`ThrottlingTests`) must `override_settings` + `cache.clear()` themselves.
- `LogoutView` always succeeds (200) even with a missing, expired, or already-blacklisted refresh cookie — never treat a non-200 from logout as meaningful.
- `ResetPasswordView` (forgot-password flow) revokes all sessions but does **not** re-issue new tokens — the frontend must route to `/login` afterward. `ChangePasswordView` (authenticated, know-your-old-password flow) does the opposite: revoke *and* immediately re-issue for the calling session.
- Google and GitHub login share one anti-hijack invariant: on **first sight** of a provider id, auto-linking/creating from the email claim only happens if the provider itself reports the email as verified; a **returning** user (matched by `google_id`/`github_id`) skips that check entirely, and linking is refused outright if the matched email is already linked to a *different* provider id (`GitHubAccountConflictError`-equivalent `ValidationError` for Google).
- The `GITHUB_LOGIN_NONCE_COOKIE` is explicitly `SameSite=Lax` regardless of `AUTH_COOKIE_SAMESITE` — it must survive exactly one top-level GET redirect back from github.com, which `Lax` allows but `None` (used for the JWT cookies in prod) isn't required for.
- `github_integration/oauth_views.py`'s `GitHubCallbackView` is the *same* callback URL for both "log in via GitHub" and "connect a GitHub repo to an existing account" (`github_integration` app) — don't confuse `accounts/github_auth.py` (login/account-linking) with `github_integration/` (repo analysis OAuth + webhooks); they share only the OAuth App and this one callback view.
- `PendingRegistration.purge_expired()` is called on write paths (registration), not from a scheduler — this project has no periodic task runner (see root CLAUDE.md).
- `Profile`/`PendingRegistration` OTP fields are HMAC-peppered (`OTP_PEPPER_KEY` falling back to `SECRET_KEY`), not a bare hash — a 6-digit code's keyspace (10^6) is small enough that a bare SHA-256 dump would be exhaustible in under a second without the pepper.
- `PWNED_PASSWORDS_ENABLED` is `not _RUNNING_TESTS` — the HIBP check makes a live HTTPS call on every password set, disabled during `manage.py test` but still present (and unit-testable) in `AUTH_PASSWORD_VALIDATORS`.
- `ProfileSerializer` never returns `is_staff` — `AuthContext.jsx`'s `checkIsAdmin()` has to probe an admin-only endpoint (`adminStats()`) instead, and treats network/5xx failures as "indeterminate" (denied but flagged), distinct from a clean 401/403 ("not admin").

## Related features
- `frontend-app` (or equivalent) — `api.js`'s CSRF/refresh machinery and `AuthContext.jsx`'s session-restore/admin-probe pattern are used by every authenticated page, not just auth screens.
- `github-integration` — the repo-analysis GitHub OAuth App/webhook pipeline shares the OAuth App and callback view (`github_integration/oauth_views.py`) with GitHub login, but is otherwise a distinct feature (PR analysis, Fernet-encrypted stored tokens).
- `infra-cross-cutting` (or equivalent) — `core/throttling.py`'s scope pattern, `_RUNNING_TESTS` settings relaxation, and `ResilientRedisCache` cache backend are shared infrastructure this feature depends on but doesn't own.
- `admin-api` (`adminapi` app) — `AuthContext.jsx`'s admin detection depends on an `adminapi` endpoint's 401/403 behavior.
